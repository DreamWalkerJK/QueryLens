一、最终目标

实现一个面向开发者和 DBA 的数据库慢查询与执行计划分析桌面工具，暂定名称 QueryLens。

默认工作目录：

D:\Documents\Code\QueryLens

技能参考仓库：

D:\Documents\Code\SkillTree

目标数据库：

\- MySQL
\- PostgreSQL
\- SQL Server
\- GaussDB

主要用户流程：

创建数据库连接
→ 检测版本与诊断能力
→ 采集或导入慢查询
→ 按 SQL 指纹聚合
→ 查看执行计划
→ 比较计划与性能变化
→ 导出诊断报告

交付结果必须是真正的桌面应用，具备可运行程序、可操作界面、本地持久化、实际数据库适配器和验证记录。

三、Git 版本控制和阶段性交付要求

必须使用 git-commit-convention-skill skill 管理提交信息和阶段性交付。

1\. 开始修改前执行并检查：
&#x20;  \- git status --short
&#x20;  \- git branch --show-current
&#x20;  \- git remote -v
&#x20;  \- git log -5 --oneline
2\. 如果当前分支不是专门用于本项目的工作分支，创建或切换到：
&#x20;  \- codex/querylens-implementation
&#x20;  如果该分支已经存在，先确认它属于当前项目并继续使用。
3\. 不直接向 main、master 或其他受保护分支提交。
4\. 不执行 git reset --hard、git clean -fd、强制推送或覆盖已有远程提交。
5\. 如果工作区已有用户未提交修改：
&#x20;  \- 不覆盖这些修改。
&#x20;  \- 不把与当前阶段无关的文件加入提交。
&#x20;  \- 必要时记录修改边界后再开始。
6\. 每个里程碑必须遵循以下顺序：
&#x20;  \- 完成该里程碑的代码和文档。
&#x20;  \- 运行该阶段适用的格式检查、构建和测试。
&#x20;  \- 检查 git diff 和 git status。
&#x20;  \- 只暂存属于该里程碑的文件。
&#x20;  \- 检查暂存区 diff，确认没有密码、Token、连接字符串、测试数据库凭据或无关修改。
&#x20;  \- 使用 git-commit-convention-skill 生成并校验提交信息。
&#x20;  \- 创建一个语义清晰、范围明确的 commit。
&#x20;  \- commit 成功后立即 push 到当前远程分支。
7\. 提交主题必须遵循：
&#x20;  \<type>(\<scope>): \<description>
8\. type 只能使用：
&#x20;  \- feat
&#x20;  \- fix
&#x20;  \- refactor
&#x20;  \- perf
&#x20;  \- docs
&#x20;  \- chore
&#x20;  \- revert
&#x20;  \- test
&#x20;  \- style
&#x20;  \- build
&#x20;  \- ci
9\. scope 必须存在，且应简洁说明受影响的模块或关注点。
10\. 提交主题必须是单行，包含类型、scope、冒号和一个 ASCII 空格，总长度不超过 72 个 Unicode 字符。
11\. 示例提交信息：
&#x20;  \- feat(connection): add database capability detection
&#x20;  \- feat(plans): parse SQL Server showplan XML
&#x20;  \- feat(ui): add slow query analysis workspace
&#x20;  \- test(dialects): cover PostgreSQL fingerprint cases
&#x20;  \- perf(parser): reduce allocations in log import
&#x20;  \- docs(support): add GaussDB validation matrix
&#x20;  \- chore(build): configure Windows desktop publishing
12\. 如果仓库中存在 git-commit-convention-skill 的验证脚本，使用它验证最终提交主题；如果脚本不可用，也必须人工检查相同规则。
13\. 第一次推送使用：
&#x20;  git push -u origin <当前分支>
&#x20;  后续阶段使用：
&#x20;  git push
14\. push 成功后把 commit hash、分支名和推送结果记录到 docs/progress.md。
15\. 如果 commit 成功但 push 因远程不存在、认证失败、网络故障或权限不足而失败：
&#x20;  \- 不删除本地 commit。
&#x20;  \- 不谎称已经 push。
&#x20;  \- 记录准确的失败原因和待执行命令。
&#x20;  \- 继续完成本地可执行的工作。
&#x20;  \- 最终报告中明确列出“已提交但未推送”的 commit。
16\. 已经 push 的提交不要随意 amend、rebase 或重写历史；除非用户明确要求。
17\. 每个 commit 应代表一个完整、可理解、可验证的阶段，避免一次提交包含整个项目所有未验证功能。

建议阶段：

\- commit 1：项目初始化、桌面壳和核心解决方案
\- commit 2：本地数据库与连接管理
\- commit 3：MySQL/PostgreSQL 适配器

四、技术方向

默认采用：

\- .NET 10 / C# 14。
\- Avalonia + MVVM，Windows x64 作为必须验证和交付的平台。
\- SQLite 保存本地连接元数据、查询快照、计划和分析结果。
\- 成熟的数据库驱动，固定经过验证的兼容版本。
\- 内置依赖注入、结构化日志、CancellationToken 和异步 IO。
\- 核心分析逻辑不依赖桌面 UI，便于独立测试。
\- 基于 capability 的数据库适配器契约。

如果现有仓库已有合理的桌面技术栈，优先沿用，并记录原因。跨平台架构不等于所有平台已经验证，交付报告应如实列出实际测试的平台。

不要为了套用模式而引入完整 DDD、微服务、消息队列或大量无实际职责的抽象。

五、数据库连接与能力检测

实现：

\- 连接配置的新建、编辑、复制、测试和删除。
\- 主机、端口、数据库、认证方式、TLS 和超时配置。
\- 密码通过操作系统凭据存储或受保护的本地存储保存。
\- 普通配置、日志、异常和导出文件中不得出现明文密码。
\- 连接建立后读取真实数据库产品、版本和兼容模式。
\- 展示可用、不可用、权限不足和未验证的诊断能力。
\- 每种采集方式展示所需的最小权限及其影响。
\- 连接失败、TLS 错误、认证失败、权限不足和超时必须有可操作的错误说明。

GaussDB 要求：

\- 不把“GaussDB”当成单一产品和单一协议。
\- 明确区分实际连接的产品形态、版本、兼容模式及可用驱动。
\- 不把 PostgreSQL 或 MySQL 协议兼容当成系统视图、统计字段和执行计划格式完全兼容。
\- 使用可扩展的能力模型及明确的产品适配层。
\- 如果缺少真实 GaussDB 环境，完成有官方依据的适配逻辑、离线样例分析、契约测试和接入说明，并列出待真实实例验证的项目。
\- 不得宣称尚未验证的 GaussDB 能力已经完整支持。
\- 如果驱动或产品形态需要用户补充信息，集中提出一次必要问题，同时推进其他工作。

六、慢查询采集

至少提供两种入口：

A. 连接数据库读取已有统计和计划信息。

B. 导入本地慢查询日志、查询统计快照和执行计划文件。

数据库特性按实际版本实现并验证：

\- MySQL：
&#x20; \- performance\_schema 的语句摘要统计。
&#x20; \- 慢查询日志导入。
&#x20; \- EXPLAIN JSON。
\- PostgreSQL：
&#x20; \- pg\_stat\_statements 的能力检测和统计读取。
&#x20; \- EXPLAIN JSON 文件导入。
&#x20; \- 估算计划分析。
\- SQL Server：
&#x20; \- Query Store 或 DMV 的能力检测。
&#x20; \- 查询统计读取。
&#x20; \- Showplan XML。
\- GaussDB：
&#x20; \- 依据目标产品官方文档和真实能力提供对应采集方式。

约束：

\- 默认只读。
\- 不自动启用扩展、Query Store、慢日志或修改数据库全局参数。
\- 提供需要 DBA 执行的初始化或权限脚本，但不擅自运行。
\- 采集具备超时、取消、最小采样间隔、批次限制和结果数量限制。
\- 处理计数器重置、实例重启、统计条目淘汰和快照缺失。
\- 统计增量只在可比较快照间计算。
\- 不把累计统计中的平均耗时冒充窗口平均耗时。
\- 数据源没有原始样本或直方图时，P95/P99 显示为不可用，不能从均值推算。

七、SQL 指纹与聚合

实现：

\- 原始 SQL、脱敏 SQL、规范化 SQL 和指纹分离存储。
\- 使用支持目标方言的解析或词法方案。
\- 正确处理字符串、注释、转义、参数占位符、标识符引用和多语句输入。
\- 不使用简单正则替换作为跨数据库 SQL 指纹的唯一实现。
\- 指纹包含必要的数据库、方言和归一化版本信息。
\- 保留数据源原生 query\_id、digest 或 query\_hash。
\- 展示调用次数、总耗时、平均耗时、数据源提供的最小/最大耗时、行数及其他可用指标。
\- 支持按时间、连接、数据库、指纹和标签筛选。
\- 原始 SQL 可能包含业务数据，默认导出脱敏内容，原文导出需用户显式选择。

八、执行计划分析

实现：

\- 树形执行计划浏览。
\- 原始 JSON/XML 查看。
\- 节点详情、父子关系、扫描类型、索引、连接方式、排序、聚合和可用运行指标。
\- 区分估算行数和实际行数、估算成本和实际耗时。
\- 区分不同数据库的 cost 单位，禁止跨引擎直接比较成本数值。
\- 展示数据库来源、版本、采集方式和时间。
\- 支持保存计划基线，并对比相同数据库语义下的后续计划。
\- 比较索引变化、扫描方式变化、连接顺序、行数偏差、排序或溢出等有依据的变化。
\- 计划中缺少的字段显示缺失，禁止填造默认性能数据。

SQL 执行边界：

\- 默认获取估算计划或读取已存在的计划。
\- 不自动运行 EXPLAIN ANALYZE、实际执行计划采集或其他会执行 SQL 的操作。
\- 实际执行分析必须是单独的用户动作，显示准确 SQL、目标连接、超时和执行风险。
\- 只允许受约束的单条查询模式；对不可证明安全的语句拒绝执行。
\- 不能仅凭 SELECT 前缀或只读事务断言没有函数、锁或外部副作用。
\- SQL Server 的 SHOWPLAN 等会话设置使用隔离连接，并在 finally 中清理，避免污染连接池。

九、诊断建议

提供基于规则且可解释的建议，例如：

\- 估算行数与实际行数偏差。
\- 大范围扫描。
\- 可能低效的分页。
\- 排序和临时数据开销。
\- 查询计划明显变化。
\- 数据源暴露的缺失索引线索。
\- 统计信息可能过期。
\- 连接顺序或过滤下推异常。

每条建议包含：

\- 触发证据。
\- 适用数据库和版本。
\- 严重度和置信程度。
\- 验证步骤。
\- 可能代价和误报情况。

不自动创建索引或改写并执行业务 SQL。

AI 诊断不是完成基础功能的依赖，第一版无需接入外部模型。

十一、测试与验收

实现并运行：

\- 各方言 SQL 指纹测试。
\- 计划 JSON/XML 解析与未知节点兼容测试。
\- 不完整或损坏文件导入测试。
\- 统计重置和增量计算测试。
\- 密码及 SQL 敏感信息脱敏测试。
\- 连接取消、超时、权限不足测试。
\- 可用环境中的 MySQL、PostgreSQL、SQL Server 集成测试。
\- GaussDB 独立的兼容性和验证状态记录。
\- 桌面关键操作冒烟测试，实际启动并检查布局和交互。
\- 本地数据迁移和版本升级测试。
\- 数据库驱动异常和连接池释放测试。

使用本地容器或用户明确提供的测试数据库验证，不对生产数据库造压。

性能记录应包括：

\- 测试环境。
\- 数据库版本。
\- 输入规模。
\- 查询数量。
\- 计划节点数量。
\- 导入耗时。
\- 解析耗时。
\- 峰值内存。
\- CPU 使用情况。
\- 并发度。
\- 结果准确性。

不得只给无依据的“高性能”结论。
